# `text_word_limit` is a 題組-level setting, not a per-小題 setting

`文本字數限制` (`text_word_limit`) governs the shared `文本` of a 題組 and is settable only at the request (題組) level. It is not a legal member of 各小題配置, even though the current schema still accepts the per-小題 form until the removal work lands. The per-小題 form is removed by #642 in the web surface, #643 in the backend fan-out, and #644 in the schema. This is a stage-ownership decision, not merely a consequence of 文本 being shared.

The decisive argument is a pipeline-stage mismatch. The shared core first calls the 文本生成器 and parses its result: `client.generate_json(...)` produces `text_raw`, and `parse_text_shell_fn` consumes it (`src/common/generation_core.py:216-220`). Only after extracting the plan does the core construct the 子題產生器 and pass that already-produced `text_raw` into each per-小題 prompt (`src/common/generation_core.py:222-255`); the calls are submitted through a `ThreadPoolExecutor` for the N-parallel stage (`src/common/generation_core.py:346-359`). The 子題產生器 therefore receives 文本 as an already-produced input/placeholder, not as something it authors. A `text_word_limit` attached to a slot arrives after the only stage that can constrain generated 文本, so it is structurally inert and can only add noise to the per-小題 contract.

The request-level path reaches the correct authoring stage and stays. The 社會領域 and 自然科學 text-prompt builders insert `params.text_word_limit` as `**文本字數上限**` in the 文本生成器 user prompt (`src/social_studies/context_builder.py:1060-1064`, `src/natural_sciences/context_builder.py:724-730`). By contrast, the current `_with_text_word_limit` helpers copy the request value into every slot (`src/social_studies/cli.py:94-114`, `src/natural_sciences/cli.py:166-187`), and the 各小題配置 blocks emit that slot value as `文本字數上限` (`src/social_studies/context_builder.py:663-698`, `src/natural_sciences/context_builder.py:454-487`). #643 reverses this fan-out and removes the per-slot emission while preserving the request-level prompt path.

The data model supports the same ownership boundary. Neither subject's `SubQuestion` has a `文本` field: the social-studies model lists the 小題's `題目` and answer fields without `文本` (`src/social_studies/schemas.py:223-246`), and the natural-sciences model does likewise (`src/natural_sciences/schemas.py:83-106`). `question_word_limit` and `option_word_limit`, however, are fields of each subject's `SubQuestionConfig` (`src/social_studies/schemas.py:150-168`, `src/natural_sciences/schemas.py:65-80`), so they describe content owned by the 子題產生器 and remain per-小題. The absence of a 小題-owned 文本 field is evidence for the pipeline-stage decision, not the decision by itself.

This ADR supersedes in part the third paragraph of ADR 0014, which says that 社會領域 and 自然科學 fan the request-level value into each slot's config and that 數學 will follow suit (`docs/adr/0014-math-gains-text-and-subquestions-via-sub-question-count.md:9`). That fan-out is reversed, and the instruction for 數學 to follow it is cancelled. The existing `user_passage` plus `text_word_limit` validation is untouched: `_math_validate_params` still raises for a non-empty user-authored `passage` when the limit is supplied (`server/generate/subjects.py:463-466`). ADR 0023 changes ownership of generated 文本 only; it does not trim or silently ignore user-authored 文本 and does not change that HTTP 422 rule.

The compatibility cost is deliberate. The subject `SubQuestionConfig` models forbid extra fields (`src/social_studies/schemas.py:150-154`, `src/natural_sciences/schemas.py:65-69`), and the resolved wire dictionaries are passed directly through `SubQuestionConfig.model_validate(item)` (`src/social_studies/cli.py:393-398`, `src/natural_sciences/cli.py:321-327`). The browser-side `isSubQuestionConfig` guard checks the listed known properties but has no closed-key or unknown-property check (`web/src/lib/formDraft.ts:30-55`), and `loadDraft` accepts fields that pass that guard (`web/src/lib/formDraft.ts:146-185`). Initial parameter objects likewise preserve each object-shaped `subquestion_configs` row, including unknown keys that are not `undefined` (`web/src/components/ParamForm.tsx:86-89`, `web/src/components/ParamForm.tsx:322-327`, `web/src/components/ParamForm.tsx:1264-1272`). Consequently, a saved draft or bookmarked URL carrying a per-小題 `text_word_limit` will restore in the browser, then be rejected server-side with HTTP 422 after #644 deletes the field from the subject schema. No decode-time shim or draft migration is part of this decision.

## Considered Options

**Tolerate-then-drop at decode time** — Rejected because it would make stale data appear accepted while silently discarding a submitted setting. It would hide the incompatibility at exactly the boundary where the strict subject model can explain it, and would weaken the confirmation contract that the displayed payload is the payload the server will use.

**Tolerate plus a client-side draft migration** — Rejected because a migration could clean local storage but could not reliably rewrite every bookmarked URL or externally retained request. It would also add a one-off compatibility path for a setting that was never meaningful at the 子題產生器 stage. The explicit 422 is the smaller and more honest compatibility surface.

**Honour only the first or minimum per-小題 row** — Rejected because a shared 文本 has no principled first 小題 and no reason to use the minimum of unrelated slot settings. Either rule would turn an invalid ownership model into an arbitrary request-level value, while leaving the per-小題 UI and wire shape misleading.

**Reorder 文本生成器 to run after the 子題 plan** — Rejected because the established core authors the 文本, 核心問題, 取材來源 and 小題 plan before the per-小題 calls (`src/common/generation_core.py:216-255`). Reordering would redesign the shared pipeline and its prompt contract merely to make a misplaced setting appear active; it would not give `SubQuestion` a 文本 field or justify a per-小題 limit.

## Consequences

After #642, #643 and #644, `text_word_limit` has one meaning and one path: a request-level limit consumed by the 文本生成器 for the 題組's shared 文本. `question_word_limit` and `option_word_limit` remain per-小題 because they describe the `題目` and options produced by each 子題產生器; no per-小題 文本 limit remains. The stale-draft HTTP 422 described above is an accepted cost, not something this ADR mitigates with a shim or migration.

The follow-up tickets remove the old surface in order: #642 removes the web per-小題 control and its forwarding, #643 removes `_with_text_word_limit` fan-out and the 各小題配置 prompt emission, and #644 deletes `text_word_limit` from the subject `SubQuestionConfig` schemas. ADR 0014 is superseded only for its fan-out statement and its cancelled 數學 follow-on instruction; its user-authored `passage`/`text_word_limit` HTTP 422 rule remains intact.
