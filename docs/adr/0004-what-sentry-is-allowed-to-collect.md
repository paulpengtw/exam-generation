# Sentry's automatic data collection is disabled unless deliberately enabled

The web app is adopting Sentry tracing, session replay, logs, and metrics, and the FastAPI backend is instrumented too. SDK v10's `dataCollection` defaults include user identity, HTTP request and response bodies, gen-AI prompt and completion content, cookies, headers, and query-parameter values. Since `/generate` streams a whole generated 題組 over SSE and the backend calls Anthropic and OpenAI directly, those defaults would send generated exam content and teacher identity through several independent channels. Both frontend and backend therefore pin `dataCollection` explicitly: `userInfo: false`, `httpBodies: []`, gen-AI input and output disabled, `cookies: false`, and `urlQueryParams: { allow: [] }`. Session replay retains `maskAllText` and `blockAllMedia` and unmasks only allowlisted app chrome, so 文本, 題目, 答案, and figures never leave the browser readably. Only logs at `WARNING` and above are forwarded. The deliberate exception is `Sentry.setUser({ id: email, email })`, which is explicit and is always sent regardless of `dataCollection`; it attributes issues to a teacher and prefills the bug-report form.

The magic-link flow places an auth token in `/verify?token=...&email=...`, and tracing or replay can record that URL. A `beforeSend` and `beforeSendTransaction` hook strips it because `urlQueryParams` controls structured parameter fields, not the raw URL in replay navigation breadcrumbs.

## Considered Options

Accepting the SDK defaults and scrubbing later with a `beforeSend` regular expression was rejected because content arrives through spans, breadcrumbs, log bodies, and gen-AI span attributes, and a scrubber would have to catch every route forever. Leaving text unmasked and marking generated regions with `.sentry-mask` was rejected because that denylist fails open: a new component leaks until it is tagged, while the allowlist fails closed. Relying on Sentry's built-in sensitive-key denylist for the token query parameter was rejected because probable protection is not a sufficient basis for an auth credential.

## Consequences

Replays preserve the shape of masked text, but a defect such as the wrong 題型 rendering is invisible: the replay shows the click, not the value. The email address is also `user.id`, leaving no non-PII handle; anonymising later loses issue attribution entirely, which is accepted so a teacher reporting a problem need not enter their own name. Log forwarding is filtered by level rather than content, so a future `logger.warning("... %s", user.email)` passes through; the durable protection is to keep identity out of log message bodies. Data already sent to Sentry cannot be unsent, so reversing this policy changes only future collection.
