# Research #721 — Does the proposed UI stack fit this Vite app?

**Date:** 2026-09-12

## Answers

1. **shadcn/ui:** Yes. The Vite/Tailwind v4 integration coexists with the existing `@tailwindcss/vite` plugin and compiles Button and Sonner after two small repository-specific fixes: remove TypeScript 6's deprecated `baseUrl` and suppress the generated Button variant export's Fast Refresh lint warning.
2. **AICSS:** The registry `ThinkingState` and all seven `@aicss/react` components render in Vite/jsdom without Next.js `transpilePackages`; however, importing the package into the type-checked application currently fails `tsc -b` on four unused declarations in its shipped `orbs/Orb.tsx`.
3. **Animation:** Motion is React 19-compatible and is the strongest fit for coordinated JS state, presence, layout, and reduced-motion behavior, but its isolated probe added 126.57 kB gzip of JavaScript; `tw-animate-css` and native CSS/View Transitions are materially cheaper for CSS-owned interactions and route/dialog transitions.
4. **Tests/replay:** `AnimatePresence` exits resolve in jsdom with real timers and `waitFor`; tw-animate-css classes remain inspectable but do not animate in jsdom; none of the candidates adds a wrapper that requires `sentry-unmask`.
5. **Size:** The existing full app stayed at 991.71 kB JavaScript / 296.16 kB gzip after unused probe imports were excluded from the application entry; shadcn's CSS baseline grew from 33.46 to 48.12 kB, and the isolated candidate costs are recorded in the table below.

## Question 1 — Does shadcn/ui fit the existing Vite/Tailwind v4 app?

### Initialization and generated files

The first direct `npx shadcn@latest init` was blocked only by the read-only npm cache described above. The successful retry used the same CLI with the writable cache and Vite template:

```text
$ npx --yes --cache /tmp/exam-generation-npm-cache shadcn@latest init -t vite
shadcn@4.21.0
```

The prompts were accepted with the Vite target, `Base UI (Recommended)`, the `Nova - Lucide / Geist` preset, and the neutral base colour. The resulting [`web/components.json`](../../web/components.json) records the result: `style: "base-nova"`, `rsc: false`, `tailwind.css: "src/index.css"`, `baseColor: "neutral"`, CSS variables enabled, Lucide icons, and the `@/components`, `@/lib/utils`, `@/components/ui`, `@/lib`, and `@/hooks` aliases. The CLI version and registry metadata are also in the resolved `web/node_modules/shadcn/package.json` and the npm registry entry at [npmjs.com/package/shadcn](https://www.npmjs.com/package/shadcn).

The init changed [`web/src/index.css`](../../web/src/index.css) from the repository's single `@import "tailwindcss";` line to a Tailwind v4 stylesheet containing:

- `@import "tailwindcss";`
- `@import "tw-animate-css";`
- `@import "shadcn/tailwind.css";`
- `@import "@fontsource-variable/geist";`
- a dark-mode `@custom-variant`
- an `@theme inline` block mapping color, radius, font, chart, and sidebar tokens to custom properties
- neutral `:root` and `.dark` OKLCH variables
- a base layer applying border, outline, background, text, and font utilities.

The generated files from init are [`web/components.json`](../../web/components.json), [`web/src/lib/utils.ts`](../../web/src/lib/utils.ts), and the stylesheet changes. The later `button` and `sonner` add created [`web/src/components/ui/button.tsx`](../../web/src/components/ui/button.tsx) and [`web/src/components/ui/sonner.tsx`](../../web/src/components/ui/sonner.tsx). The dependency changes are visible in [`web/package.json`](../../web/package.json) and its lockfile: `@base-ui/react`, `@fontsource-variable/geist`, `class-variance-authority`, `cn`, `lucide-react`, `shadcn`, `tw-animate-css`, then `next-themes` and `sonner` for the two components. The Button implementation uses Base UI and CVA rather than assuming Radix UI; that is the selected Nova preset's source, not an inference from a blog post.

### Aliases, Tailwind plugin, and PostCSS

The original repository did not have an `@/*` alias. The CLI refused to initialize until a valid alias existed; after adding the alias to the TypeScript project configuration and Vite resolver, the generated `@/...` imports resolved. The final explicit alias setup is:

- [`web/tsconfig.json`](../../web/tsconfig.json) and [`web/tsconfig.app.json`](../../web/tsconfig.app.json): `"@/*": ["./src/*"]`.
- [`web/vite.config.ts`](../../web/vite.config.ts): `@` resolves to `path.resolve(__dirname, "./src")`.
- [`web/vitest.config.ts`](../../web/vitest.config.ts): the same alias is needed for jsdom tests.

I intentionally did not retain the CLI's `baseUrl`: TypeScript 6's build failed with `TS5101`, saying that `baseUrl` is deprecated and will stop functioning in TypeScript 7. Removing only `baseUrl` while keeping `paths` and the Vite aliases made the project type-check without weakening the rest of the compiler settings.

The existing `tailwindcss()` call remains in [`web/vite.config.ts`](../../web/vite.config.ts), and there is no generated `postcss.config.*`. The build therefore confirms that shadcn's Tailwind v4 CSS imports coexist with the current `@tailwindcss/vite` plugin; this matches the official [shadcn Vite installation](https://ui.shadcn.com/docs/installation/vite), which uses the Vite plugin path rather than requiring PostCSS. `tw-animate-css` is a CSS import, not a replacement Vite plugin; its package source and installation instructions are at [npmjs.com/package/tw-animate-css](https://www.npmjs.com/package/tw-animate-css).

### Validation

After init, the first `npm run build` failure was the TypeScript 6 `baseUrl` diagnostic above. The first `npm run lint` failure was the generated `button.tsx` export of `buttonVariants`, rejected by the repository's `react-refresh/only-export-components` rule. A file-local disable was added for that intentional CVA factory export. After those adjustments, and after adding Button and Sonner, the targeted shadcn Vitest probe passed and the normal build, lint, and test commands passed. The full final test run was 109 files and 830 tests passed. The shadcn-specific probe is [`web/src/research/StackFitShadcnProbe.test.tsx`](../../web/src/research/StackFitShadcnProbe.test.tsx); it renders Button and Toaster together and stubs jsdom's missing `matchMedia` API, which Sonner/next-themes reads.

**Finding:** adoptable in this app, with the alias and TypeScript 6/lint adjustments recorded above. It does not ask the app to switch from the existing Vite Tailwind integration to PostCSS.

The generated [`web/src/ThinkingState.tsx`](../../web/src/ThinkingState.tsx) contains a `"use client"` directive and imports a CSS module. In this Vite app the directive is harmless, Vite handles the CSS module, and [`web/src/research/StackFitAicssProbe.test.tsx`](../../web/src/research/StackFitAicssProbe.test.tsx) rendered the component in jsdom successfully. The package's own [`web/node_modules/@aicss/react/package.json`](../../web/node_modules/@aicss/react/package.json) declares React and React DOM peers `>=18`, depends on `lucide-react`, exports each component as a subpath, and ships its source files and CSS modules. The actual probe is [`web/src/research/StackFitAicssPackageProbe.test.tsx`](../../web/src/research/StackFitAicssPackageProbe.test.tsx), and the package's export map and component source are the primary implementation sources. ```text

Vite's runtime transform and Vitest both work; the package is not ready to import into a strict `tsc -b` application without upstream cleanup, a compiler-policy change, or a local packaging workaround.

**Finding:** the registry drop-in is a good fit. The published package is runtime-compatible and React-compatible, but its current shipped source is not clean under this repository's strict TypeScript build, specifically when `Orb` is type-checked.

## Question 3 — Which animation option fits each surface?

### Candidates and evidence

`motion@13.2.0` was installed and imported from `motion/react`:

```text
$ npm --cache /tmp/exam-generation-npm-cache install motion
added 4 packages, and audited 578 packages in 3s
```

The npm registry metadata for [motion](https://www.npmjs.com/package/motion) declares React peer support as `^18.0.0 || ^19.0.0`. The probe uses the APIs documented in [AnimatePresence](https://motion.dev/docs/react-animate-presence), [layout animations](https://motion.dev/docs/react-layout-animations), [reduced motion](https://motion.dev/docs/react-use-reduced-motion), [transitions](https://motion.dev/docs/react-transitions), and [MotionConfig](https://motion.dev/docs/react-motion-config): `AnimatePresence` for exit, `layout` for list/disclosure layout, `useReducedMotion`, and a shared `MotionConfig` transition.

The installed `tw-animate-css` package is CSS-only. Its source and parameter documentation ([package](https://www.npmjs.com/package/tw-animate-css), [animation-duration docs](https://github.com/Wombosvideo/tw-animate-css/blob/main/docs/parameters/animation-duration.md)) support Tailwind animation utilities and CSS custom properties. A direct JavaScript import was intentionally tested and removed; Vite reported:

```text
Error: "." is not exported under the conditions ["node", "development", "import"] from package .../node_modules/tw-animate-css (see exports field in package.json)
```

That is expected for a stylesheet package. The working integration is the global CSS import in `web/src/index.css`, not a JS import.

The native probe uses the platform `<dialog>` API (`showModal()`/`close()`), `dialog:open`, `@starting-style`, and discrete `display`/`overlay` transitions. These are documented by MDN's [`<dialog>` reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog) and [`@starting-style` reference](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40starting-style). The route option is the [View Transition API](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API), with React Router's data-router integration documented at [reactrouter.com/how-to/view-transitions](https://reactrouter.com/how-to/view-transitions). The repository already uses a data router (`web/src/routes.tsx`, `web/src/App.tsx`) and `useBlocker` in `web/src/pages/GeneratePage.tsx`; a view transition can decorate a permitted navigation, but it does not replace the blocker.

### Surface comparison

| Surface | Motion | `tw-animate-css` alone | Native CSS / View Transitions | Result |
|---|---|---|---|---|
| Pending/done/failed button | State-driven `motion.button` animation, shared defaults via `MotionConfig`, and `useReducedMotion` | State/data-attribute classes and keyframes; no JS orchestration | CSS transitions/keyframes and custom properties | Motion is convenient if the icon/content sequence is JS-owned; CSS is sufficient for a simple style swap. |
| QuestionCards entering a streaming list | `AnimatePresence` plus `layout` handles enter/exit and reflow | Enter classes are easy; exit requires state/class choreography and manual removal; no FLIP/layout model | CSS enter/exit is possible with classes; View Transitions are better for a document snapshot than a continuously growing list | Motion is the cleanest fit for item presence and reflow. |
| Native `<dialog>` / `showModal()` | Possible, but React must coordinate Motion's visual state with top-layer `showModal()` and `close()` | Can style a stateful dialog, but does not own top-layer lifecycle | `@starting-style` plus `dialog:open` and discrete `display`/`overlay` transitions directly fit the platform lifecycle | Prefer native CSS for this existing `DestructiveConfirm` dialog. |
| Disclosure expansion | `layout` and `height: "auto"` are direct | Utility/keyframe or max-height recipes; no measurement/layout orchestration | CSS can handle simple known-size transitions; custom properties can supply the shared timing | Motion is useful for dynamic content; CSS is adequate for fixed/simple content. |
| Data-router route changes | Requires a location-keyed presence/layout shell and can coexist with router blockers | Does not capture route snapshots | Browser View Transitions plus React Router's `viewTransition`/`useViewTransitionState` integration target this exact case | Prefer the router/native route integration, with feature detection; keep `useBlocker` for unsaved form protection. |

### One timing token set

The CSS probe puts `--motion-duration` and `--motion-ease` on the element and consumes them in `duration-(--motion-duration)`, `ease-[var(--motion-ease)]`, and native `transition` declarations. This gives CSS and the browser APIs one direct token set. Motion's documented transition API accepts JavaScript values such as `{ duration: 0.2, ease: "easeOut" }`, and `MotionConfig` centralizes those JS defaults; it does not document `var(--motion-duration)` as a transition duration that Motion reads from computed CSS. A shared token file or a small adapter that reads computed CSS into JS is therefore needed for exact Motion/CSS synchronization. This is why the Motion probe uses `MotionConfig` while the CSS/native probes use custom properties rather than claiming direct interchangeability. See Motion's [transition](https://motion.dev/docs/react-transitions), [animation](https://motion.dev/docs/react-animation), and [CSS](https://motion.dev/docs/css) documentation.

**Finding:** do not make the animation library a blanket dependency for every surface. Use Motion where React presence/layout/reduced-motion state is the problem; use tw-animate-css for small CSS-owned states; use native dialog transitions and View Transitions for platform/router lifecycle work.

## Question 4 — What do tests and Sentry Replay observe?

### Vitest/jsdom probes

[`web/src/research/StackFitMotionProbe.test.tsx`](../../web/src/research/StackFitMotionProbe.test.tsx) renders an `AnimatePresence` exit with a 50 ms Motion transition. After the hide click, the exiting node remains in the DOM; with real timers, `waitFor` observes `onExitComplete`, after which the node is removed. The targeted test passed 2/2. No fake timers were needed; fake timers would require explicitly advancing Motion's scheduled frames/timers and add unnecessary coupling to the test.

[`web/src/research/StackFitTwAnimateProbe.test.tsx`](../../web/src/research/StackFitTwAnimateProbe.test.tsx) renders `animate-in`, `fade-in`, `slide-in-from-bottom-2`, and CSS-variable duration/easing classes. The targeted test passed 1/1 and confirmed the classes and custom properties are present. jsdom reports `animationName: "none"` and does not run a compositor, so there is no CSS animation completion event or timer to await. This is a class/contract test, not a visual animation test.

The native dialog probe is [`web/src/research/StackFitNativeCssProbe.tsx`](../../web/src/research/StackFitNativeCssProbe.tsx). Its `showModal()` behavior is a browser integration and is not meaningfully exercised by jsdom's layout/compositor; browser-level coverage would be needed for actual top-layer and transition behavior.

### Replay masking

The replay integration in [`web/src/sentry.ts`](../../web/src/sentry.ts) sets `maskAllText: true`, `blockAllMedia: true`, and only unmask-allowlists `.sentry-unmask`. ADR [0004](../adr/0004-what-sentry-is-allowed-to-collect.md) establishes the fail-closed masking policy, and ADR [0005](../adr/0005-replay-is-buffered-and-flushed-on-feedback.md) establishes buffered replay and feedback-triggered flushing.

Motion's `motion.*` elements render the requested underlying DOM element; `AnimatePresence` and `MotionConfig` do not add a semantic wrapper. tw-animate-css adds no runtime element, and the native probe animates the actual `<dialog>`. AICSS and Sonner do create their own internal DOM, but none adds `sentry-unmask`, so generated exam text remains masked. Any future unmasking should be an explicit app-boundary decision for static chrome only, consistent with ADR 0004.

**Finding:** Motion's exit lifecycle is testable in jsdom with real timers and async assertions; CSS animation timing is not. The candidate libraries do not bypass the app's replay policy or require new `sentry-unmask` opt-outs.
